## 1. Solution layout [Proposed]

Two projects in one solution under `backend/` in this repository. Name: **`VehicleManagementDM`** (owner, 2026-11-26). It is the code name only; the app's display name is still OI-04.

```text
├─ VehicleManagementDM.sln
├─ .config/dotnet-tools.json        dotnet-ef pinned as a local tool (dev machine only)
├─ src/VehicleManagementDM.Api/      the API (Microsoft.NET.Sdk.Web, net8.0)
│  ├─ Program.cs                     composition root only: registrations + pipeline
│  ├─ appsettings.json               non-secret defaults only (repo is public)
│  ├─ appsettings.Development.json
│  ├─ Properties/launchSettings.json, PublishProfiles/
│  │

│  │  ├─ Trips/                      start, swap, hand-over, cancel, end, history
│  │  ├─ Transfers/

│  │  └─ Audit/
│  │     (each folder holds: <X>Controller.cs, <X>Service.cs, Dtos/ (requests + responses))
│  │
│  ├─ Domain/
│  │  ├─ Entities/                   EF entity classes (shared across features)

│  │  │                              global exception handler, SQL error translator (§5)

│  │  ├─ Storage/                    file store: unique names, validation, save/read/delete (§11)
│  │  ├─ Time/                       IClock (server UTC), GST helpers for report day-splits
│  │  └─ Paging/                     PageRequest / PagedResult<T>
│  │
│  └─ BackgroundJobs/                reminder job, log-retention job (BackgroundService)
│
└─ tests/VehicleManagementDM.Api.Tests/   xUnit: unit tests + API integration tests (WebApplicationFactory)
```

**Why this shape**
- **Feature folders**: everything about trips sits in `Features/Trips`. Easy to find, easy to change, and it avoids a 40-file `Controllers/` folder.
- **Controllers → services → `AppDbContext`**: controllers stay thin (HTTP only); services hold business rules; EF Core's `DbContext` is already a unit of work, so no repository layer on top.
- **One API project**: a separate Domain/Application/Infrastructure project split adds ceremony without benefit at this size. The folders keep the same boundaries, so splitting later stays possible.
- **Template**: same SDK and target framework as the reference. API controllers only (`AddControllers`), without the MVC `Views/` part, because this API serves no pages.

## 2. Packages [Proposed]

All NuGet packages ship inside the publish folder, so nothing is installed on the server.

| Package | Why |
|---|---|
| `Microsoft.EntityFrameworkCore.SqlServer` 8.0.x | ORM + SQL Server provider |
| `Microsoft.EntityFrameworkCore.Design` 8.0.x (dev-only asset) | Creating migrations |
| `Swashbuckle.AspNetCore` | Swagger UI for development |
| Tests: `xunit`, `Microsoft.NET.Test.Sdk`, `Microsoft.AspNetCore.Mvc.Testing` 8.0.x | Tests |

**Deliberately not used** (built into .NET 8 instead): Serilog, AutoMapper, MediatR, FluentValidation, ASP.NET Core Identity tables, Hangfire. Password hashing uses `PasswordHasher<T>` from the shared framework; validation uses DataAnnotations; mapping is written by hand; jobs use `BackgroundService`.

## 3. Database and migrations (D-029, D-030)

**Flow**

```text
Developer changes an entity / configuration
  → dotnet ef migrations add <Name>        (dev machine; creates a migration file)
  → commit the migration with the model change
  → publish + deploy
  → on startup the API runs Database.Migrate():
       database missing      → created, then all migrations applied
       migrations pending    → applied in order
       already up to date    → nothing happens
```

- EF Core can't change the database without a migration file; the `migrations add` step is what turns a model change into a schema change. A test runs `dotnet ef migrations has-pending-model-changes` (available from EF Core 8) and **fails if a model change has no migration**, so nothing slips through.
- **Startup never crashes because of the database.** If the database is unreachable at startup, the API still starts, logs the failure, and retries the migration in the background. Until it succeeds every request gets the JSON error `503 DATABASE_NOT_READY` (§5). Reason: a crashed .NET app on IIS shows IIS's own HTML error page, which D-032 forbids.
- **First admin (AUTH-06):** when the Users table is empty after migrating, the initializer creates the first admin from configuration (`Seed:FirstAdmin:*`, set as server environment variables, never in git). With no seed configured it does nothing.
- **Destructive changes** (dropping or renaming columns) are reviewed by hand in the generated migration before commit. Records are never deleted (BR-08), so most changes are additive.
- **SQL login [Proposed]:** the app gets its own SQL login, `db_owner` of its own database only (needed to run migrations), never `sa`/sysadmin. The first database creation needs `dbcreator`, or our team creates the empty database once by hand.
- **Concurrency:** `rowversion` columns on vehicles, trips, transfers and lots, plus filtered unique indexes (e.g. one Active trip per vehicle). Two people scanning the same vehicle at the same moment: one succeeds, the other gets `409`.
- **Times:** stored as UTC `datetime2`; the API returns ISO-8601 UTC (`...Z`); the app shows GST (BR-01). Reports split hours by GST calendar day on the server (RPT-04).

## 4. Authentication and authorization (D-031)

**Mechanism:** ASP.NET Core cookie authentication (built-in), with users in the app's own `Users` table (staff and admins, a `Role` column). No ASP.NET Core Identity tables.

| Concern | Design |
|---|---|
| Login | `POST /api/v1/auth/login` with ID + password + rememberMe. On success the API sets the auth cookie and returns the user profile and role. ID is case-insensitive (AUTH-03) |
| Login IDs | Staff: `DM` + YY + 5 digits, e.g. `DM2600042` (D-011). Admin: **`ADM` + YY + 5 digits**, e.g. `ADM2600001` (D-037). Generated by the API, separate sequences, never reused. The staff-prefix setting may not be set to `ADM` |
| Cookie | `HttpOnly`, `Secure` (HTTPS only), `SameSite=Strict`, its own name (e.g. `vms.auth`), encrypted by ASP.NET Core Data Protection |
| Remember me (AUTH-02) [Proposed] | `rememberMe=true` → persistent cookie, 30 days sliding. Otherwise a 12-hour cookie |
| Instant deactivation (AUTH-07) | Each user has a `SecurityStamp` copied into the cookie. On every request the API checks the user is still active and the stamp still matches. Deactivation, password reset or password change rotates the stamp, so every existing session ends immediately |
| Lockout (AUTH-08) | 5 failed attempts → locked for 15 minutes (`FailedLoginCount`, `LockoutEndUtc`) |
| Passwords | `PasswordHasher<T>` (PBKDF2, salted), never stored or logged in plain text |
| Login abuse | Built-in rate limiter on the login endpoint |
| Roles | `[Authorize(Roles = "Admin")]` / `"Staff"` on every controller. The server checks every permission; the app only hides things (D-007). Ownership checks (e.g. "own trips only") live in the services |
| No redirects | Cookie events are overridden: not logged in → `401` JSON, wrong role → `403` JSON. Never a redirect to a login page |
| Data Protection keys [Proposed] | Persisted to a folder on the server outside the publish folder, encrypted with Windows DPAPI. Without this, every app restart or app-pool recycle would log everyone out |
| CSRF | The only client is the native app (no web portal). `SameSite=Strict` + JSON-only request bodies cover it |
| CORS | Not enabled: browsers are not a client, and CORS doesn't apply to native apps |
| Flutter side (Phase 8) | The app keeps the cookie in a persistent cookie jar stored in the platform's secure storage, and sends it automatically |
| HTTPS certificate (D-036) | The server uses a self-signed certificate. The app accepts it with an `HttpOverrides` whose `badCertificateCallback` returns `true` for **every** certificate (owner's code). `Secure` cookies still work. **Accepted risk:** the app doesn't verify the server, so someone on the same network can intercept IDs, passwords and session cookies. Safer option, same effort: accept only our certificate's SHA-256 fingerprint (pinning) |

This replaces the "short-lived access tokens with refresh tokens" line in `REQUIREMENTS.md` §8 (D-031).

## 5. Errors: one JSON format for everything (D-032)

### 5.1 The format [Proposed]

Every non-2xx response, from any source, has this body, with `Content-Type: application/problem+json`. It follows the internet standard for API errors (RFC 9457 "Problem Details") plus two fields of our own (`code`, `errors`).

```json
{
  "status": 409,
  "code": "VEHICLE_NOT_AVAILABLE",
  "title": "Vehicle not available",
  "detail": "Vehicle D 01423 is on an active trip and can't be started.",
  "errors": null,
  "traceId": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01"
}
```

| Field | Use in the app |
|---|---|
| `status` | HTTP status, repeated for convenience |
| `code` | Stable machine code. The app branches on this (e.g. show "Try again" for `DATABASE_UNAVAILABLE`). Never changes once published |
| `title` | Short heading for an error dialog |
| `detail` | The real, specific, user-readable message. The app shows this |
| `errors` | Field errors for forms: `{ "registrationNumber": ["Registration number already exists."] }`; `null` otherwise |
| `traceId` | Shown small in the app ("Ref: …"); finds the exact log entry (§6) |

Success responses are the plain resource JSON (no wrapper); the HTTP status says success or failure.

### 5.2 Error catalogue [Proposed]

| Situation | Status | `code` | Message to the app |
|---|---|---|---|
| DTO validation failed (missing/invalid fields) | 400 | `VALIDATION_FAILED` | Real field messages in `errors` |
| Malformed JSON / wrong data type in body | 400 | `MALFORMED_REQUEST` | Which field or position is wrong |
| Not logged in / cookie expired / session ended | 401 | `UNAUTHENTICATED` | "Your session has ended. Please sign in again." |
| Wrong ID or password | 401 | `INVALID_CREDENTIALS` | "Staff ID or password is incorrect." (never says which) |
| Account locked | 401 | `ACCOUNT_LOCKED` | Includes when the lock ends |
| Account deactivated | 401 | `ACCOUNT_DEACTIVATED` | Real message |
| Logged in but wrong role / not your record | 403 | `FORBIDDEN` | Real message |
| Record not found | 404 | `NOT_FOUND` | "Vehicle not found." etc. |
| Unknown URL | 404 | `ROUTE_NOT_FOUND` | Method + path |
| Wrong HTTP method | 405 | `METHOD_NOT_ALLOWED` | |
| Duplicate value (unique index hit) | 409 | `DUPLICATE_VALUE` | Field-level: "Registration number already exists." |
| Someone changed the record first (rowversion) | 409 | `CONCURRENCY_CONFLICT` | "This record was changed by someone else. Reload and try again." |
| Business rule broken | 409 | Specific, e.g. `VEHICLE_NOT_AVAILABLE`, `STAFF_HAS_ACTIVE_TRIP`, `LOT_INACTIVE`, `VEHICLE_MISMATCH` | Real rule message |
| Body too large | 413 | `PAYLOAD_TOO_LARGE` | Size limit |
| Wrong content type | 415 | `UNSUPPORTED_MEDIA_TYPE` | |
| Too many login attempts (rate limit) | 429 | `TOO_MANY_REQUESTS` | Retry time |
| Database unreachable / connection failed | 503 | `DATABASE_UNAVAILABLE` | "The server can't reach the database. Try again shortly." |
| Database still migrating at startup | 503 | `DATABASE_NOT_READY` | |
| Database timeout / deadlock | 503 | `DATABASE_TIMEOUT` | "Try again." |
| Schema mismatch (missing table or column) | 500 | `DATABASE_SCHEMA_ERROR` | Real description in Development (see 5.4) |
| Uploaded file wrong type, unreadable or too big | 400 / 413 | `INVALID_FILE` / `PAYLOAD_TOO_LARGE` | Allowed types and size (§11) |
| Requested file missing on disk | 404 | `FILE_NOT_FOUND` | |
| Any other unexpected exception | 500 | `INTERNAL_ERROR` | See 5.4 |

`SqlException` numbers are translated centrally: connection/network errors and timeouts → 503; unique violations 2601/2627 → 409 with the field resolved from the index name; invalid object/column 208/207 → schema error; `DbUpdateConcurrencyException` → 409.

### 5.3 How "never HTML" is guaranteed

| Source of the error | Handled by |
|---|---|
| Exceptions thrown anywhere | .NET 8 `IExceptionHandler` (global) |
| Business-rule failures | Services throw typed `AppException`s (`NotFoundException`, `ConflictException`, `ForbiddenException`…) carrying the `code` and message |
| DTO validation | `ApiBehaviorOptions.InvalidModelStateResponseFactory` replaced with our format |
| Empty-body status codes (unknown route 404, 405, 415) | Status-code-pages middleware writes our JSON |
| Authentication / authorization | Cookie `OnRedirectToLogin` / `OnRedirectToAccessDenied` overridden → 401 / 403 JSON |
| Rate limiter | Rejection callback writes our JSON |
| Database down at startup | §3: app starts anyway and answers 503 JSON |
| Developer exception page | Not used, even in Development (same format; more detail, see 5.4) |
| IIS itself (if hosted on IIS, OI-13) | `web.config` `httpErrors existingResponse="PassThrough"` so IIS doesn't replace our JSON. Limit: if the .NET process can't start at all, IIS shows its own page before our code runs. §3 makes that practically only a broken deploy |

### 5.4 "Send the true error" and its limit (approved 2026-11-26)

- All **known** errors (validation, auth, not found, duplicates, business rules, database unavailable/timeout) always send the **real, specific message**. This covers almost every error a user sees.
- **Unexpected** errors (bugs, unknown exceptions, schema errors) controlled by one setting, `Errors:IncludeExceptionDetails`:
  - **Development = true:** `detail` holds the real exception message plus `exceptionType`.
  - **Production = false (owner approved):** `detail` says "Something went wrong on the server. Ref: <traceId>"; the full exception is in the log (§6).
  - Reason: raw exception text can include SQL, table names, server paths or data. Sending it to every phone is a security risk (OWASP). The traceId gives support the true error in seconds.
- Stack traces are never sent to the app.

## 6. Logging (D-032)

- **Where [Proposed]:** an `ErrorLogs` table in the app's own database. If the database itself is the problem (can't connect), the entry goes to a daily file instead (`logs/errors-YYYY-MM-DD.jsonl`, folder set in config, outside the publish folder).
- **What:** every error response, 4xx and 5xx, plus background-job and startup failures. 5xx and database errors store the full exception; 4xx store the code and message (no stack). Every entry has the `traceId` that was sent to the app.
- **Fields:** time (UTC), traceId, level, status, code, HTTP method, path, user ID and role (if logged in), exception type, message, stack trace, inner exception, client IP, app version (from a request header).
- **Never logged:** passwords, cookies, request bodies, signature images.
- **Retention:** a background job deletes database entries and fallback files older than **30 days** (owner, 2026-11-26; a setting), protecting the 10 GB Express limit.
- Normal diagnostics (startup, migrations applied, jobs) use .NET's built-in `ILogger` to the console / the IIS stdout log. No third-party logging library.

## 7. API conventions [Proposed]

| Topic | Convention |
|---|---|
| Base path | `/api/v1/...` (version in the URL, no versioning package) |
| Style | Resource-oriented REST; actions as sub-resources: `POST /api/v1/trips/{id}/end`, `/swap`, `/handover`, `/cancel` |
| JSON | camelCase; enums as strings; dates ISO-8601 UTC |
| Lists | `?page=1&pageSize=20` → `{ items, page, pageSize, totalCount }`; filters as query parameters |
| IDs | `int` identity keys internally. QR codes carry a random, non-guessable token, never an ID (QR-01) |
| Validation | DataAnnotations on request DTOs; cross-field rules via `IValidatableObject`; business rules in services |
| Mapping | Hand-written entity ↔ DTO mapping; entities never leave the API |
| Transactions | Multi-step actions (start trip, swap, end, transfer departure) run in one transaction |
| Live data (D-035) | No push, polling or SignalR. Each screen loads data when opened and on manual pull-to-refresh. Trip timers tick in the app from the server's start time, so they stay correct without reloading |
| Health | `GET /health` → app + database status (built-in health checks) |
| Swagger | On in Development; off in Production unless a setting enables it |
| Config and secrets | Connection string, first-admin seed, key paths come from environment variables on the server and `dotnet user-secrets` on the dev machine. Nothing secret in git (public repo) |

## 8. Request pipeline (order)

```text
Exception handler (JSON)  →  Status-code pages (JSON)  →  HTTPS redirection / HSTS
→  Database-ready gate (503 while migrating)  →  Routing  →  Rate limiter
→  Authentication (cookie + session check)  →  Authorization  →  Controllers
```

## 9. Background jobs

| Job | What | Interval |
|---|---|---|
| Startup migrator | Applies migrations, retries while the database is down (§3) | Startup, then retry |
| Reminders (TRP-06, TRF-07) | Finds trips/transfers past the reminder delay, sends push notifications every 30 min, writes the reminder log | Every minute |
| Log retention | Deletes error logs and fallback files older than 30 days (§6) | Daily |

Push sending sits behind `IPushSender`, a no-op for now (D-039): reminders appear in the in-app notification list. FCM/APNs plugs in later (needs Firebase and Apple accounts) without touching the job.

QR images and PDF labels are built in the Flutter app; the API only returns label data (D-040).

## 10. Testing

- **Unit tests:** business rules in services (start checks, swap, hours by segment, midnight split, occupancy formula).
- **Integration tests:** the real API in memory (`WebApplicationFactory`) against a throwaway database on the local SQL Server Express. Covers auth (cookie, lockout, deactivation), every error code in §5.2 and its JSON shape, and migrations from an empty database.

## 11. Files: photos and signatures (D-034)

| Topic | Design |
|---|---|
| Where | A folder on the server, set by `Storage:RootPath`. **Outside the publish folder**, so a deploy never overwrites or deletes files. Subfolders: `vehicles/`, `staff/`, `signatures/`. The app-pool / service account needs write access |
| Name | The API generates every name: a new GUID + the extension of the **detected** type, e.g. `3f2a9c0e1b7d4e6f9a8b2c4d6e8f0a1b.jpg`. The client's file name is ignored |
| Database | Stores **only the file name** (e.g. `Vehicle.PhotoFileName`, `TripSegment.SignatureFileName`). The folder comes from configuration, so the storage can move without touching data |
| Upload | Photos: `multipart/form-data` to the owning record (e.g. `PUT /api/v1/vehicles/{id}/photo`). Signature: a base64 PNG inside the start-trip / hand-over request, so the trip and its signature are saved in one call |
| Validation | JPEG or PNG only (signatures PNG only), checked by the file's content (magic bytes), not its name. Limits (settings): **photo 20 MB** (D-042), signature 512 KB. Otherwise `INVALID_FILE` / `PAYLOAD_TOO_LARGE` |
| Request size | Photo endpoints accept 21 MB (`[RequestSizeLimit]` + multipart limit); every other endpoint 1 MB. 20 MB is under Kestrel's 30 MB and IIS's ~28.6 MB defaults; `web.config` sets it explicitly. Uploads stream to disk, never fully into memory |
| Who can view | Vehicle photos: everyone logged in. Staff photos: admins, the staff member, and staff in the hand-over picker. Signatures: admins and the staff member on their own trips |
| Consistency | Save to a temporary name → commit the database → rename to the final name. If the database step fails, the file is deleted, so there are no orphan files and no records pointing at missing files |
| Replacing a photo | New file and name; the old file is deleted after the database commit. Signatures are never replaced (they are trip history) |
| Access | Only through the API: `GET /api/v1/files/{kind}/{name}`, **logged in only**, with the same permission checks as the record (staff see their own signatures and all vehicle photos; admins see all). Never a public static folder: photos, signatures and licence data are personal data (REQUIREMENTS §8). The name must match the GUID pattern, so paths like `../` are impossible |
| Caching | Names never change, so responses are `Cache-Control: private, max-age=31536000, immutable`; the app caches images |
| Backups | A database backup doesn't include these files. The storage folder must be backed up with the database (Phase 10) |

**Implementation notes (M1):**
- Settings are read through the options system when first used, never while services are registered, so every configuration source (environment variables, user-secrets, test overrides) applies.
- HTTPS redirection is not used: the session cookie is `Secure`, so it is simply never sent over plain HTTP.
- **M2:** edits of shared records use `rowVersion` (optimistic concurrency); the audit interceptor writes `AuditLogs` rows for every admin change in the same transaction as the change; vehicle history moves to M4 and staff trips / hand-over picker to M3 (D-045).
- **M3:** every trip action runs in one transaction under SQL Server application locks (`sp_getapplock`) on the staff member(s), vehicle(s) and trip involved, taken in a fixed order so actions can't deadlock; the filtered unique indexes (one active trip per staff member and per vehicle) are the final guard. Tested with two phones starting the same vehicle at once.
- **M4–M6:** transfers use the same app-lock pattern as trips (`Common/Database/AppLocks`); "busy" (BR-02, D-026) is one shared rule for trips and transfers (`DutyRules`); the reminder job (`BackgroundJobs/ReminderJob`) claims each due reminder with a conditional update so it is sent once; push goes through `IPushSender`, registered as the approved no-op until Firebase exists (D-039). Release: `Properties/PublishProfiles/FolderProfile.pubxml` (framework-dependent), `web.config` (JSON errors pass through IIS, 21 MB request filter), `appsettings.Development.json` excluded from publish; runbook in `DEPLOYMENT.md`.
- The ASP.NET Core exception-middleware log is silenced in `appsettings.json` because `ErrorLogWriter` already logs every error once.
